# 本地规则与 AI 流式解读设计

## 目标

在现有占问结果页中增加两层解读，避免结果只罗列卦辞、爻辞与结构资料：

1. 成卦后立即生成可复核的本地规则解读。
2. 由用户主动请求 AI 深度解读，并将模型内容真实流式显示。
3. AI 服务不可用时，本地解读和原有经传资料仍可完整使用。
4. 所有措辞保持为研读与行动提示，不声称确定预测。

## 已确认方案

采用“GitHub Pages 静态前端 + Cloudflare Worker + Workers AI”的组合方案。

前端保留纯静态部署。本地规则引擎不依赖网络；Cloudflare Worker 负责输入校验、限流、提示词组装、模型调用和流式转发。AI 解读生成成功后随占问记录保存在当前浏览器，Worker 不建立解读内容数据库。

## 用户体验

### 本地解读

六爻成卦后，本地解读立即出现在原文资料之前，按以下顺序展示：

1. 核心判断：把所问、本卦主题和主要变化连接为一句简明判断。
2. 当前处境：结合本卦卦象与主题说明当前状态。
3. 关键变化：按现有变爻取法突出本次主要爻位，不平均解释全部爻辞。
4. 后续趋势：将之卦描述为条件性的变化方向，而非必然结果。
5. 行动建议：给出两到三项可执行或可观察的事项。

现有“经文原文、变爻规则、卦象结构、易理提示、经传互参”继续作为解读依据展示在后方，不删减原始资料。

### AI 深度解读

本地解读下方提供“AI 深度解读”按钮。用户点击后：

1. 按钮暂时禁用，防止同一次请求重复提交。
2. 页面不显示进度条、百分比、预计时间或等待动画。
3. Worker 将模型生成的文本立即转发，前端收到一句便显示一句。
4. 内容依次展开为核心判断、当前处境、关键变化、后续趋势和行动建议。
5. 不使用前端模拟的逐字动画；页面显示的是模型真实返回流。
6. 完整响应结束后，将 AI 解读和生成时间写入该次本地历史记录。

如果流式响应中断，页面保留已经收到的内容，在末尾显示错误原因和重试操作，但不缓存不完整内容。重试会发起一次新的完整生成。

历史记录已有完整 AI 解读时直接展示缓存结果，不自动再次请求模型。用户可以主动重新生成；新结果成功完成后覆盖旧缓存。

## 本地规则引擎

新增独立的纯函数模块，输入只包含：

- 用户问题；
- 本卦与之卦资料；
- 动爻索引；
- 现有 `readingRule` 的主要阅读爻位；
- 对应的卦辞和爻辞。

输出为固定结构：

```js
{
  category,
  summary,
  situation,
  turningPoint,
  trend,
  actions,
  cautions,
  evidence
}
```

问题类别通过有限关键词识别为事业、关系、学业、财务、健康或通用主题。类别只调整观察角度和行动用语，不改变卦象数据，也不宣称理解用户未提供的事实。

解读的组合依据是：

- 本卦的卦象文字与现有主题摘要；
- 初、二、三、四、五、上六个阶段的通用时位含义；
- `readingRule` 选出的主要爻辞；
- 本卦到之卦的主题变化；
- 无动爻和多动爻时的不同阅读规则。

所有用户输入和经文在写入页面前经过文本转义。解读统一使用“提示”“倾向”“可考虑”“需要留意”等条件性措辞。

## AI 请求与流式协议

前端只向 Worker 发送生成解读所需的结构化资料，不允许浏览器指定系统提示词、模型或输出上限。请求包含：

- 本次问题；
- 本卦和之卦名称、上下卦、主题摘要；
- 卦辞；
- 变爻规则和主要爻辞；
- 本地规则解读。

Worker 在服务端拼装固定提示词，要求模型：

- 仅依据所给资料分析；
- 不伪造经典出处；
- 区分原文、传统取法和现代研读建议；
- 不作医疗、法律、财务等专业结论；
- 使用五个约定标题，并控制整体长度。

Worker 使用 UTF-8 流式响应转发模型文本。前端以 `ReadableStream` 读取真实数据块，保留跨数据块的半行缓冲，并识别以下标题：

```text
【核心判断】
【当前处境】
【关键变化】
【后续趋势】
【行动建议】
```

标题和正文均通过 DOM `textContent` 写入，不执行模型返回的 HTML。响应完成前不把内容标记为可缓存结果。

## Worker 安全与限流

Worker 使用 Workers AI binding，模型名由服务端环境配置决定。前端不能读取 Cloudflare 凭据，也不能改变模型配置。

请求限制：

- 仅接受 `POST` 和必要的 `OPTIONS` 请求；
- 校验 `Origin`，只放行配置的 GitHub Pages 域名和明确列出的本地开发地址；
- 仅接受 JSON，并设置请求体与每个字段的长度上限；
- 校验卦序、动爻数量、爻位和文本类型；
- 单次模型输出上限默认约 900 token。

限流默认值：

- 每个来源 IP 每小时最多 5 次；
- 全站每天最多 50 次；
- 限额通过 Worker 环境变量调整，不由前端控制。

IP 在 Worker 内与私有盐值组合后哈希，KV 只保存按时段过期的匿名计数键和全站计数。Worker 不主动记录问题、卦象、模型输出或原始 IP，也不在错误日志中输出请求正文。

KV 计数属于成本保护而非严格计费系统；并发请求可能带来小幅计数误差。模型账户仍应设置平台侧预算或免费额度上限，作为最终成本边界。

## 错误处理

Worker 返回稳定的错误码，前端映射为简短中文提示：

- `INVALID_REQUEST`：请求资料不完整或超出限制；
- `ORIGIN_NOT_ALLOWED`：来源域名未授权；
- `RATE_LIMITED`：单 IP 请求过于频繁；
- `DAILY_LIMIT_REACHED`：当日全站额度已用完；
- `MODEL_UNAVAILABLE`：模型暂时不可用或额度不足；
- `STREAM_INTERRUPTED`：响应中途断开；
- `SERVICE_ERROR`：未分类的服务异常。

错误不会遮挡或清除本地解读。流式中断保留临时内容但不写入历史缓存；用户重开历史记录时只看到上一次完整缓存。

## 本地历史记录

历史记录结构增加可选的 `aiReading` 字段：

```js
{
  text,
  generatedAt,
  modelLabel,
  version
}
```

导入旧版历史记录时该字段缺失仍为合法数据。导出与导入保留完整 AI 解读。模型内部标识不必向用户暴露，`modelLabel` 只用于未来区分解读来源。

## 测试与验收

自动化测试覆盖：

1. 0 到 6 个动爻的所有取法分支。
2. 六种问题类别和无匹配关键词时的通用类别。
3. 本卦与之卦相同、乾坤六爻皆变以及缺失可选资料的处理。
4. 用户问题和模型文本的 HTML 转义。
5. 正常流式响应、标题跨数据块、UTF-8 字符跨块和中途断流。
6. 成功缓存、不完整内容不缓存、历史记录兼容与导入导出。
7. Worker 的方法、Origin、输入校验、单 IP 限流和每日限额。
8. AI 服务失败时本地解读仍可阅读。
9. 桌面和移动视口中，流式增长不遮挡按钮、原文或后续内容。

验收标准是：用户成卦后无需网络即可先读到连贯结论；主动请求 AI 后能立即看到真实流式内容；服务失败不会损害本地结果；刷新或打开历史记录可以恢复最后一次完整 AI 解读。

## 部署

部署文档将提供以下流程：

1. GitHub Pages 发布静态前端。
2. Cloudflare 创建 KV namespace、Workers AI binding 和 Worker 环境变量。
3. 设置允许的生产域名、本地开发域名、限流值和哈希盐。
4. 部署 Worker 并把公开端点配置到前端。
5. 验证 CORS、流式响应、每日限额和历史缓存。

仓库只提交配置示例，不提交账户凭据、私有盐值或其他 secret。

## 后续路线：人工校订解读库

后续第三阶段可建设人工校订的六十四卦与 384 爻现代解读库，为每一卦和每一爻分别维护主题、处境、风险、行动与出处说明。该内容库可逐步替代当前通用时位模板，提高离线本地解读的精度与文本质量，并继续作为 AI 解读的可靠依据。

这一阶段需要独立的版本、出处、校订和内容验收流程，不纳入本次实现范围。
